# BlueBubbles stock plugin implementation spec

Register BlueBubbles as a bundled Rust adapter with platform key `bluebubbles`. Start after Buzz and the shared gate. A headless Mercury profile serves authorized iMessage conversations through an operator-managed BlueBubbles Server on a Mac. The bridge supports native text and files, and helper-backed features apply only when qualified. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [Buzz spec](BUZZ_ADAPTER_SPEC.md) · [Hermes BlueBubbles guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/bluebubbles.md)

## Bridge and webhook ownership

Put the factory and REST client in `hermes-gateway::messaging::bluebubbles`. Configure the trusted server origin, API credential and separate receiver URL privately. Establish identity with authenticated ping and server info, and verify the intended Mac user/server and Messages account. Scope chat and GUID aliases to that qualified installation. Keep one active owner for the binding and rotate or disable through fenced generations. Report API readiness, real webhook delivery and Private API helper availability independently. The standard REST path relies on a functioning Messages user session. The operator qualifies helper-dependent modes separately. [Mercury adapter seam](src/messaging/types.rs) · [BlueBubbles API and webhooks](https://github.com/BlueBubblesApp/bluebubbles-docs/blob/master/server/developer-guides/rest-api-and-webhooks.md)

Use the authenticated REST API to provision an installation-specific webhook for new and updated messages. Record registration ID and ownership and reconcile on restart. Remove or replace only that registration under the current lease. A lost registration response requires an exact lookup before trying again. The provider accepts a receiver URL, so use a rotating receiver secret distinct from the REST password and a private listener or trusted TLS path to the Mac. Redact URLs bearing that secret from all logs. Authenticate the configured slot before parsing bounded payloads. Disable mismatched server routes even if the payload resembles a valid message. Acknowledge only on durable dispositions or staged preparation. [Hermes webhook setup](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/bluebubbles.md#how-the-webhook-is-registered)

## Intake, recovery and routing

Use the verified installation, canonical chat GUID and original message GUID as durable evidence. Match email and international phone/handle aliases to a verified existing DM, retaining the original alias without multiplying sessions. Keep group GUID and participant policy separate from any sender's personal route. A sender-only event cannot default an unknown group to a DM. Suppress own output and Tapback notifications as inputs. Use compatible updates to hydrate a pending item or apply a typed content change, preserving original identity and admitting at most once. Treat webhook delivery as a hint where payload provenance or scope needs an authenticated REST read. Use bounded authorized message-history repair by exact chat and message anchors where the qualified server supports it. Stage overlapping live copies and report unfilled history. A first binding establishes a baseline. [Hermes inbound mapping](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/bluebubbles/adapter.py#L574) · [BlueBubbles server releases](https://github.com/BlueBubblesApp/bluebubbles-server/releases)

Apply sender grants, DM pairing, group policies and optional exact text or spoken addressing. A spoken-addressing check requires explicit enablement and staged audio under verified actor and room policy. Keep denied media out of turns. Native commands, approval and clarification are text-based. Use listed current participant evidence for any protected read or effect. Remember verified source message for native replies when helper and macOS release support that operation. Preserve source thread intent or report it unavailable. Authorized helper reactions, read receipts and typing are separately enabled effects and must not leak presence or state to a refused incoming actor. [Hermes BlueBubbles capabilities](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/bluebubbles.md#features) · [BlueBubbles helper](https://docs.bluebubbles.app/helper-bundle/installation)

## Delivery and media

Stage allowed image, video, audio and document references via the same authenticated server. Bound byte count and stream time, verify type and restrict redirects. Preserve attachment-only inputs and transcribe supported voice through the host. Render plain text with clickable URLs and bounded paragraph chunks. Send ordered text and native attachments through confirmed chat GUIDs. If the owner provisions a new DM by verified phone/email, require the helper capability and treat chat creation with its first message as one external operation. Confirm both exact chat and first-message receipts before sending more parts. Enforce correct service and delivery mode when a Mac exposes multiple account or carrier paths. [Hermes chat resolution and dispatch](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/bluebubbles/adapter.py#L372)

Generate a stable `tempGuid` for each prepared operation. Record output message GUIDs, verified ownership and exact helper/effect scope. Associate an authenticated own-message observation only with the same attempt and destination. Retain uncertainty after an ambiguous call unless exact provider evidence or a verified replay guarantee settles it. A `tempGuid` alone does not authorize automatic retransmission. Record confirmed local/server submission independently of remote delivery. Never move a restarted reply to the home channel by default. An approved home can receive its own scheduled, webhook and manual results through the same profile outbox. [Shared delivery](ADAPTER_CONTRACT.md#delivery-and-recovery)

## Implementation and acceptance

| Step | Prerequisite | Evidence |
| --- | --- | --- |
| Bridge and inbound records | Buzz live acceptance and shared gate | Verified Mac/account, owned webhook lease, duplicate and repair handling. |
| Replies, helper and files | Durable intake and verified chat | DM/group policy, native commands, media, capability-gated helper effects and ordered outbox. |
| Live acceptance | Transport and shared conformance | Current BlueBubbles/macOS pairs and real iMessage clients prove the advertised standard and helper modes. |

Use scripted BlueBubbles REST responses and webhook posts through the production adapter and real profile owner. Test two servers or Mac users reusing local IDs, stale webhook secret and slot, ambiguous create registration, duplicate and updated GUIDs, one shared alias binding, denied files, malformed content, repair and restart, and a lost `tempGuid` delivery acknowledgement. Run shared conformance and `cargo test --locked --workspace`. With a real Mac bridge, verify DM, authorized group and quote behavior, media both directions, authorized read/typing/reaction controls when available, a denied sender, and restart recovery plus a home notification. Record server version, macOS user mode, helper state and observed receipt evidence. [Hermes BlueBubbles fixtures](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/gateway/test_bluebubbles_plugin.py)

## Scope

BlueBubbles owns the Mac bridge and Messages access. Exclude macOS setup automation, legacy iMessage bridging and config compatibility, standalone sending and Desktop UI. [Backend parity scope](../../BACKEND_PARITY_PLAN.md#scope)
