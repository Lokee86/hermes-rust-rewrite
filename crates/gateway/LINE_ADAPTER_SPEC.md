# LINE stock plugin implementation spec

Register LINE as a bundled Rust adapter with platform key `line`. Start after QQ Bot and the shared gate. A headless profile serves a LINE Official Account in eligible 1:1 chats, groups and rooms, uses a reply token for timely results and exposes a durable fetch button for slow work. It stages native media and can push to approved destinations when the channel has the necessary allowance. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [QQ Bot spec](QQBOT_ADAPTER_SPEC.md) · [Hermes LINE guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/line.md) · [Next adapter, SimpleX](SIMPLEX_ADAPTER_SPEC.md)

## Registration and signed intake

Put the factory and HTTP client in `hermes-gateway::messaging::line`. Bind the channel secret, scoped access token, verified bot identity and dedicated HTTPS receiver to its profile. Use the provider bot info call and configured webhook verification, report account, receiver and media-URL readiness independently, and fence stale receiver and credential generations. Verify `X-Line-Signature` over raw bounded request bytes with the channel's HMAC-SHA256 secret before parsing. Check the destination when present and handle the valid empty verification request. Commit every item disposition or recoverable handoff before a success acknowledgement. [Mercury adapter types](src/messaging/types.rs) · [LINE webhook signature](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/)

Dedup callbacks by channel and `webhookEventId`, messages by verified LINE message ID, and actions by the native invocation. Redelivery may be out of order. Preserve provider time, source and actor as evidence, and do not change an already committed native queue position. Treat join, leave, follow, unfollow and unsend as scoped lifecycle or content changes. Actor and room grants govern DMs, groups and rooms, with unknown actors denied for protected controls. Split per-actor session routing from reply audience. Denial prevents downloads, result lookups and native execution. A restart keeps staged events and accepted dispositions. LINE redelivery is bounded and not a cursor-based history stream. [LINE receiving and redelivery](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)

## Reply, deferred results and commands

Bind each single-use reply token to its exact event, channel, actor and destination. Record the observed receipt time, absolute event age and provider limits, and reserve it once before sending. A documented redelivery can renew the usable time of that same unused grant within the provider's limits. It cannot restore a consumed or uncertain grant. Render text and permitted content in ordered groups of up to five message objects, with provider text length limits and safe Unicode chunking. Strip unsupported formatting while preserving author text and links. Use the DM-only loading animation where authorized. Interim chatter is independently typed and must not silently consume a reserved final or pending-result token. [LINE reply endpoint and token rules](https://developers.line.biz/en/reference/messaging-api/nojs/#send-reply-message)

Use an owner-configured threshold within the expected token window for the slow-turn Template Buttons notice. Bind its opaque **Get answer** action to original actor or specifically authorized group audience, route, invocation, retention and originating reply receipt. Persist a pending, ready, delivered, interrupted or expired outcome. A completion racing the notice or a user tap reads/updates the same durable final effect. A valid tap presents its own fresh reply token, with no new native turn. A pending tap returns a bounded status. A ready tap claims the committed final once, and a delivered tap returns the recorded status. Cancelled or expired work returns an appropriate scoped notice. An ambiguous final blocks subsequent attempts to send the same final until exact evidence or owner resolution. Text commands, approvals and clarification still use native execution authority. [Hermes slow-result workflow](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/line.md#slow-llm-responses)

## Media and push

Stage authorized image, audio, video and file content via LINE's message content API. Preserve file names, media IDs, stickers, and shared locations as typed data. Bound retention, media sizes and asynchronous preparation. Return audio and image/video with provider-supported HTTPS original and preview objects. Serve only the leased artifact through short-lived opaque capabilities, with bounded repeat fetches, revocation and a verified public origin. A provider client must not gain filesystem path traversal, directory listings or profile access. Publish a link or typed capability refusal for unsupported formats, including arbitrary native document uploading. [LINE Messaging API reference](https://developers.line.biz/en/reference/messaging-api/nojs/) · [Hermes media serving](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/line/adapter.py#L790)

Use Push API for approved proactive or final fallback when the reply grant expired unused or was definitively rejected and the original audience remains allowed. Apply the provider's send eligibility and quota. Reserve one stable `X-Line-Retry-Key` per supported immutable push request. Classify the provider's accepted-request evidence, including a matching duplicate acknowledgement, within the documented 24-hour window. A key does not prove acceptance outside that guarantee. The Reply API cannot use Push retry evidence. Keep ambiguous Reply sends held. A successful API result confirms acceptance, while user visibility can still depend on provider delivery and blocking rules. An authorized home ID can receive scheduled and manual sends without an open native conversation. [LINE retry protocol](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/) · [Hermes LINE home target](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/line.md#cron--notification-delivery)

## Implementation and acceptance

| Step | Prerequisite | Evidence |
| --- | --- | --- |
| Channel and intake | QQ Bot live acceptance and shared gate | Verified channel, signed batches, redelivery and refusal across restart. |
| Native turns and deferred reply | Durable intake | Scoped commands and durable fetch action through restart, cancellation and duplicate taps. |
| Media and push | Scoped outbox | Typed media, bounded capability serving and retry-key evidence. |
| Live acceptance | Transport and shared conformance | Real LINE chats plus qualified media and push, including a slow turn recovered by a fresh tap. |

Use the production adapter and native profile owner with signed HTTP and scripted LINE endpoints. Test a mixed webhook batch with a failed persistence step, lost ack, cross-channel signature and replay, unused grant redelivery, consumed token, two simultaneous actors, malicious or repeated button taps, restart before and after final commit, an accepted push with lost response, and authorized preview fetch after restart. Run shared conformance and `cargo test --locked --workspace`. Verify a real Official Account in DMs and enabled group/room contexts, signed bot join or leave, fast reply, timed pending notice and later fetch, native media, DM loading and scheduled push. Record eligibility and quota of the test account. [Hermes LINE tests](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/gateway/test_line_plugin.py)

## Scope

Exclude standalone senders and legacy Hermes configuration. LINE has no native message editing on the reference route. Desktop UI remains deferred. [Backend parity scope](../../BACKEND_PARITY_PLAN.md#scope)
