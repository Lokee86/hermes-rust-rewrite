# Gateway adapter contract v1

Mercury's gateway owns the lifetime of a channel conversation from the first authenticated event to the last recorded delivery. A stock messaging plugin is a bundled adapter with its own platform descriptor, configuration and connection factory. The native profile owner can enable each stock plugin independently.

The core polling and push conformance suite establishes the foundation. Expand and prove the [shared stock-plugin requirements](#shared-requirements-for-stock-plugins) before implementing the planned plugins. Implement and accept them in order, starting with [Discord](DISCORD_ADAPTER_SPEC.md), then [Telegram](TELEGRAM_ADAPTER_SPEC.md), then [Slack](SLACK_ADAPTER_SPEC.md).

The contract covers the native Mercury host boundary. Hermes v0.23.4 supplies the reference behavior for the platform registry, normalized messages, session scoping, and delivery. [Hermes platform registry](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/gateway/platform_registry.py) · [Hermes message events](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/gateway/platforms/event.py) · [Hermes gateway behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/developer-guide/gateway-internals.md)

## Existing code and target ownership

Mercury has one profile gateway owner, native session receipts, and a writer that commits turn history with execution authority. The messaging module already proves the adapter lifecycle, durable intake, native controls and the shared delivery outbox with synthetic transports. Routines and signed webhooks publish through that outbox. The current Telegram host has a separate poller and inbox. Telegram's adoption includes a one-time native data cutover onto the shared path. [Messaging runtime](src/messaging/runtime.rs) · [Core conformance](src/messaging/conformance.rs) · [Gateway authority](src/authority.rs) · [Telegram cutover](TELEGRAM_ADAPTER_SPEC.md#native-telegram-cutover)

| Owner | Responsibility |
| --- | --- |
| Profile gateway | Adapter registry and connection leases, verified profile binding, policy and capability checks, conversation routing, durable ingress and checkpoints, and the delivery outbox. |
| Native session authority | Queue order, execution claims and generations, interactive controls, approval and clarification state, committed history and receipts, and recovery of uncertain execution. |
| Adapter | Platform credential verification, network lifecycle, conversion of platform events and identities, formatting and delivery limits, and evidence from platform requests. |
| Engine | Provider and tool execution under the settings and permissions supplied by the gateway. |

Put the registry, ingress processing, and outbound coordinator behind a messaging module in `hermes-gateway`. Adapters call a connection-scoped ingress interface. The messaging module uses internal session admission and control methods and publishes results from committed receipts. Routines and webhooks submit outbound intents through the same coordinator. Store messaging records in the owning profile's `mercury.db`, using the existing profile database and conversation writer. Adapters use scoped host operations for staging attachments and reading reply artifacts. [Profile database](../engine/src/db.rs) · [Attachment handling](src/upload.rs)

## Interface

The gateway validates contract major version, adapter identity, configuration, and advertised capabilities before activating a connection. Version 1 requires text intake and text delivery. Negotiate additional capabilities per connection and apply the authorized destination's capabilities before preparing an effect. These include topics or threads, command and prompt interactions, streaming media and audio, and platform display operations. A capability request without support produces a typed refusal, with any supported fallback chosen by gateway policy.

| Operation | Contract |
| --- | --- |
| Register and connect | An adapter supplies its platform identifier, version, capabilities, and connection factory. The gateway binds the configured adapter to one profile, verifies the platform account, and grants a connection lease. The adapter reports readiness, retryable disconnects, or a configuration or credential failure. |
| Submit an event | The adapter presents an authenticated platform event, its replay identity, and an optional resume checkpoint. A durable result identifies acceptance, a repeat of a prior result, refusal, or conflicting reuse, and returns the stored checkpoint when one is in use. A failed commit is an explicit request to retry or resume from the last durable checkpoint. |
| Prepare a delivery | The gateway supplies a committed, authorized intent. The adapter returns an ordered, bounded plan of platform operations without performing network effects. The gateway records the plan and stable part identities before the first attempt. |
| Send a part | The adapter performs one platform operation for one leased attempt and returns classified evidence. The gateway records the result and uses it to decide whether and when another attempt can start. |
| Stop or reconnect | The gateway stops new intake and delivery claims, drains or cancels in-flight operations, and revokes the connection generation. A new connection uses the persisted checkpoint, active routes, and receipts. Stale connection generations cannot admit updates or settle attempts. |

Expose health and receipt status through the native profile owner, with the relevant profile, connection, conversation, and attempt identifiers. Credential values and message bodies stay out of operational status and diagnostics.

## Identity and policy

The gateway assigns the profile and connection scope after verifying the external account. It grants one active intake lease per platform account within a Mercury installation. When a receiver serves multiple accounts, the owner also leases that receiver. Bind each incoming event to exactly one verified account before admitting it. Platform IDs are opaque values. Labels, usernames, and message-supplied profile names have no authority.

An inbound event carries a verified chat and optional subdestination, sender and relevant membership evidence, and an event ID within the platform's replay scope. It carries normalized content or a typed control action. The gateway records two identities. The conversation binding selects the native session from the owning profile, verified account, chat, thread or topic, and policy-selected participant scope. The delivery destination records the exact original chat, subdestination kind and ID, and reply anchor when applicable. Sharing a conversation across destinations preserves each input's delivery destination and the session's turn order. Use a deterministic creation key to recover a session created before an interrupted route write. A lost mapped session is blocked pending an explicit owner decision.

Room policy determines whether a participant can submit work, whether a room shares its session, and which mentions, commands, tools, and controls are allowed. Recheck the current connection and applicable policy at intake, before claiming a turn or executing a control, and before each external delivery attempt. A credential change to another platform account creates a new connection identity. Pending work continues to refer to its original identity and destination.

Approval and clarification prompts carry gateway-issued action identities bound to the intended actor or role, conversation, pending request, and execution generation. Repeated and stale responses return their recorded decision or a typed refusal. Queue edits, steering, redirects, interruption, and prompt responses all use the same native authority as local clients. Media and remote text pass through the gateway's data and attachment policy before use by the engine.

## Intake, ordering, and execution recovery

1. Authenticate the transport and normalize the event. Record the policy revision and the minimal evidence needed to identify and replay its disposition.
2. Commit the accepted input or durable refusal, along with any safe cursor advancement. A batch checkpoint advances only through the durably handled prefix. Polling and push adapters follow their platform's acknowledgement and resume rules. A transport that cannot replay an observed gap reports it in connection status.
3. Persist the transport event receipt and derive native submission identity from the verified connection and logical input. When distinct platform events describe one logical input, record their identities as aliases of the same native receipt. An edit or control carries its own operation identity and references its target. Resolve or create the routed session within the owning profile. A repeated event identity with equal immutable data reads the original disposition. Bind refreshable authorization evidence, transport credentials and derived context separately from the replay fingerprint. Conflicting reuse preserves the original and returns a conflict.
4. Claim the queued turn under the current owner and policy. Persist the claim before starting the engine. Use the native turn boundary to commit history and the terminal result together.

The route orders ordinary inputs and replies. Authorized controls for a running turn can reach the authority while that turn is awaiting an answer. An uncertain execution fences further ordinary turns in its route until the owning authority resolves it. Other routes remain eligible for work. A restart reconciles durable intake, queued receipts, and committed results. A claim with an uncertain execution outcome enters the existing native unknown-resolution path. Retain deduplication identities through the adapter's supported replay window and for all unsettled work.

## Delivery and recovery

A reply intent references a committed turn result or a durable, authorized producer notification. The intent records the approved destination, any conversational reply anchor, and stable delivery identity. The gateway validates the rendered plan against the authorized destination and records each part with its own durable attempt and platform receipt. Parts for the same destination are sent in order. Negotiated display operations can track progress, stream previews, or update an existing platform message under the authorization of the same intent. The committed outcome determines the final reply. Expiring transport signals such as typing and native drafts carry no receipt for a durable message and do not hold destination order. A display operation that can create or mutate a durable message uses the same attempt and uncertainty rules as any other durable effect.

| Result | Gateway action |
| --- | --- |
| Confirmed | Commit the platform receipt and mark the part delivered. A restarted owner resumes from the next unfinished part. |
| Retryable with evidence of non-acceptance | Persist the retry deadline and its scope. Retry the same part after that deadline under current policy. An explicit platform rate limit is one such result. |
| Definitively rejected | Record the terminal failure and make it visible to the operator. |
| Uncertain | Hold the part and later deliveries to its destination. A missing response, ambiguous transport failure, or interrupted send claim enters this state. |

Persist each attempt before invoking the adapter. On restart, reconcile incomplete attempts while holding the new owner lease. Positive platform evidence may confirm a delivery. A configured owner can also mark the exact attempt delivered or discard it. Only confirmed non-acceptance permits an automatic retry. Resolving one attempt releases its destination's order fence and leaves other destinations independent.

## Shared requirements for stock plugins

The Discord, Telegram and Slack specs establish the common work below. Implement these requirements through the native owner, session authority and messaging store before starting the stock plugin implementations. Each platform spec defines its protocol, account and permission evidence, platform limits and effect classifications. [Discord implementation spec](DISCORD_ADAPTER_SPEC.md) · [Telegram implementation spec](TELEGRAM_ADAPTER_SPEC.md) · [Slack implementation spec](SLACK_ADAPTER_SPEC.md)

| Requirement | Shared host behavior | Conformance evidence |
| --- | --- | --- |
| Profile setup and lifecycle | Persist enabled connections and secret references in the owning profile. The private owner can configure, verify, rotate, disable and inspect them. Verify external identities before granting leases. When a receiver serves multiple accounts, bind each event and send to the verified account named by its authorized installation evidence. Fence both receiver and account generations. | Reopen saved settings, rotate and replace a credential, and contend for an account from two profiles. Send through a receiver with two verified accounts and reject ambiguous or stale routing. Check redacted status and revocation. |
| Policy and pairing | Evaluate user, room, member and operator grants, mention rules, pairing, and model, prompt, skill, tool and approval overrides. Preserve the source and revision of verified membership evidence. Recheck before protected reads, native claim, control and delivery. An operation that changes the audience must carry authority for the source and the resulting destination. Hold grants requiring unavailable evidence. | Test deny precedence, scoped pairing, parent and subdestination overrides, grant revocation, and a move from a private source to a destination that lacks permission to receive its contents. |
| Conversation binding and provisioning | Store the conversation binding separately from each immutable delivery destination. Authorize any new, shared, restored or transferred binding through the native session owner. Provision an external thread or topic as a leased host effect, then bind the returned destination under the same account and policy. A missing or uncertain destination is fenced. | Two subdestinations can share a session and receive their own replies in order. A provisioned destination survives restart. An uncertain provision holds dependent work. A stale or cross-profile restore is refused. |
| Deferred intake and contextual data | Commit event identities, logical input aliases and preparation state before advancing the checkpoint or acknowledging a push. Stage media and complete route preparation before native claim. Coalesce compatible items from the same actor and exact destination. Context reads keep their provenance and durable watermark under the authorized source and binding. Updating that watermark requires committed context. | Reopen between commit and staging, submit two kinds of event for the same message, replay overlapping batches and a late file share, and resume context hydration without starting extra turns. Revoke staged work before claim. |
| Commands and interactive outcomes | Expose typed native command descriptors with arguments, required grants, result visibility and capability availability. Route commands, skills, model selection, queue and busy-turn controls, approvals and clarification through the native authority. Persist the action identifier, actor or role, route, generation, expiry and decision. Return a scoped durable invocation or control receipt to the adapter for its time-bounded callback. Any reply handle carries the verified account, audience and expiry. Apply current access policy to each use. Resolve platform-native stop events against the bound execution generation. | A repeat reads the same decision without another effect. Test expired and wrong-actor responses, approved session or persistent grants, prompt retirement, a callback that expires before the native result, and a delayed platform stop against a later execution. |
| Ordered and observable effects | Plan destination-scoped messages, edits, prompt retirement, provisioning and file publication as typed operations. Persist each intermediate platform receipt that later steps depend on, including uploaded file IDs, provisioned topics and confirmed stream revisions. Distinguish preparation from visible publication. Persist rate-limit domains and deadlines. Use a fallback only with evidence that the original effect did not occur. | Reopen a plan with successful preparation and an unfinished publication. Reconcile an uncertain append or share. Exercise retry scope, rate limits, fallback after definite refusal, a committed final after draft expiry, and an unknown persistent preview that holds only its destination. |
| Media and audio | Stage bounded streams in private profile storage with validated references, quotas and scoped reads. Separate immutable attachment identity from expiring transport references. Route voice notes through the profile's transcription and synthesis services and return artifacts through a leased delivery. Apply the same input and file access rules to both plugins. | Test an attachment-only turn, deduplicated media, a refused or oversize fetch, cross-account artifact access denial, and voice-note transcription and a generated spoken reply. |
| Proactive and manual delivery | Bind a verified destination to the profile even before a conversation exists. Scheduled, webhook, background and authorized manual sends reference the same outbox with stable producer and request IDs. Keep the initial destination on restart and recheck it at dispatch. | Set a home destination without opening a session. Deliver a routine, a signed webhook notification and a manual reply to the intended subdestination. Replay each producer identity after restart. |

The shared interface can use the existing `AdapterFactory`, `Ingress`, `DeliveryIntent` and native session methods as its seams. Extend their typed capabilities, operations and evidence where the stock requirements need them. Keep shared fixtures independent of stock platform payloads. Use the normal profile gateway, a deterministic provider, disposable profile databases and synthetic polling and push transports. Stub the external audio service at its scoped boundary and exercise real attachment staging and receipt recovery. [Adapter types](src/messaging/types.rs) · [Core conformance](src/messaging/conformance.rs)

Build the shared additions in dependency order. Profile setup and policy establish the trusted account and actor. Conversation and destination bindings then support deferred intake, commands and producer routing. Media and audio preparation and ordered delivery use those same bindings. Exercise the combined paths before handing the interfaces to a production plugin.

## Adoption and completion

1. **Spec each stock plugin individually.** Compare its supported workflows with the existing specs. Add common host behavior and its conformance case to this contract as overlap is found. Keep platform-specific protocol and presentation decisions in that plugin's spec.
2. **Complete the shared implementation gate.** Preserve the core polling and push suite below. Implement the shared stock-plugin requirements and verify every row through the real gateway owner. Run the conformance suites and `cargo test --locked --workspace` before starting a production plugin.
3. **Adopt and accept one plugin at a time.** Use the tested gateway for routing, checkpoints, commands, admission and delivery. Where Mercury already persists platform state, migrate once under the current owner and account locks. Preserve valid configuration, inbox history and acknowledgement position. Historical rows stay visible without enqueuing turns. The shared host is the sole live writer at cutover. Complete each plugin's transport and live gates before starting the next. The current order is Discord, Telegram, then Slack. [Backend roadmap](../../BACKEND_PARITY_PLAN.md)

Use the loopback gateway, native owner checks, and scheduler and webhook tests as prior art. The conformance suite must reproduce these cases through a running gateway and reopened profile storage. [Native session tests](tests/websocket.rs) · [Owner tests](tests/owner.rs)

| Acceptance case | Required evidence |
| --- | --- |
| Profile and route isolation | A DM, a thread, and a conversation under a second profile resolve to their intended sessions. Stale connection generations and forged cross-profile controls are refused. |
| Intake and retry | Send an accepted event, an exact duplicate, a conflicting duplicate, and a forbidden input. Verify the durable dispositions, one admission for the accepted event, a resume checkpoint that never passes uncommitted input, and no admission for the forbidden input. |
| Native execution | Reopen after intake, queueing, execution claim, and result commit. Verify recovery of safe work, an explicit uncertain execution fence, and a reply based on the committed result. Confirm approvals and clarification actions require the matching request and generation. |
| External delivery | Reopen before and after claim or confirmation. Test an explicit retryable rate limit, definitive rejection, a lost acknowledgement, and operator resolution. Verify ordering of multi-part replies and continued progress in an unrelated conversation. |
| Revocation and producer routing | Remove a user's access or change an account during queued work and before delivery. Verify the current policy applies. Send a scheduled and a webhook notification through the authorized destination using the same delivery receipts. |
| Capabilities and lifecycle | Verify registration, health reporting, lease take-over, and structured refusals for missing capabilities. Exercise at least two intake transport shapes without adapter-specific rules in the gateway authority. |

The core gate requires these conformance cases and `cargo test --locked --workspace` to pass. The shared implementation gate also requires the stock-plugin cases above. Each production plugin has its own transport and live acceptance gate.
