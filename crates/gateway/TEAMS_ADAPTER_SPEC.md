# Microsoft Teams stock plugin implementation spec

Register Microsoft Teams as a bundled Rust adapter with platform key `teams`. Start after Matrix passes live acceptance and the expanded shared stock-plugin contract passes conformance. A headless Mercury profile can serve an installed Teams app in personal chats, group chats and channel threads, accept native approvals, exchange media, and deliver results after restart. The reference is Hermes v0.23.4's bundled Teams adapter and Microsoft's current Teams agent and Connector wire APIs. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [Matrix spec](MATRIX_ADAPTER_SPEC.md) · [Hermes Teams manifest](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/teams/plugin.yaml) · [Microsoft Teams agent transport](https://learn.microsoft.com/en-us/microsoftteams/platform/agents-in-teams/connect-agent-without-sdk)

## Architecture, registration and authentication

Put the factory and wire client in `hermes-gateway::messaging::teams`. Reuse the gateway HTTP server and Rust HTTP client for a dedicated public HTTPS activity endpoint, normally `POST /api/messages`, and authenticated Connector REST calls. The Teams module owns the manifest, wire validation, approved service endpoints, and Teams rendering. The profile owner supplies verified bindings, intake, policy, native command and session authority, attachment staging, and the shared outbox. Bind each public endpoint to a configured receiver slot. The native owner surface stays private. [Mercury adapter types](src/messaging/types.rs) · [Microsoft Connector REST reference](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-api-reference?view=azure-bot-service-4.0)

- **Registration and readiness.** Configure an Azure Bot resource with its Teams channel and a single-tenant Microsoft Entra app registration. Verify the app ID, tenant, cloud and credential reference through private profile setup. Generate a package using the current Teams app manifest for `personal`, `groupChat` and `team` scopes, with supported commands and only the enabled file and consent capabilities. The operator installs it in the intended Teams resources. Outbound token acquisition proves the app credential. Installation evidence and signed activity verify a usable conversation. Report listener health, credential validity, consent, verified installations and delivery health independently. Qualify the public cloud first. A different cloud must supply its complete Microsoft-published authentication and service endpoint set and pass the same gate before activation. [Microsoft bot deployment and identity](https://learn.microsoft.com/en-us/azure/bot-service/bot-builder-deploy-az-cli?view=azure-bot-service-4.0) · [Teams app manifest](https://learn.microsoft.com/en-us/microsoftteams/platform/resources/schema/manifest-schema)
- **Inbound authentication.** Bound activity JSON to 1 MiB before decoding, including chunked requests. Validate the Connector bearer token against the configured cloud's trusted OpenID metadata and signing keys, and check issuer, allowed algorithm, time bounds, audience and applicable Teams channel endorsement. Match the signed `serviceUrl` claim to the activity and validate the endpoint against approved Connector origins. Match the recipient app and authenticated activity tenant and installation to the configured receiver and account. Path hints, display names and body-supplied profile identifiers carry no routing authority. Fence receiver, account and installation changes. Refresh signing keys without accepting unverifiable callbacks during rollover. [Microsoft Connector service authentication](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-authentication?view=azure-bot-service-4.0#connector-to-bot-authentication)
- **Outbound credentials.** Use the owning bot's Entra credential for a Connector-scoped token, with serialized refresh and caching by verified app, tenant, cloud and audience. Use the app secret for ordinary Connector messaging when configured, or a supported certificate or managed identity credential. Teams file-host and Graph operations require separate audience-scoped tokens and their own permission evidence. Keep bearer tokens, signed media URLs, object details and message bodies out of public diagnostics. Reject redirects that would change the authorized recipient of a credential. [Microsoft bot-to-Connector authentication](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-authentication?view=azure-bot-service-4.0#bot-to-connector-authentication) · [Microsoft Teams file authentication](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/bots-filesv4#authenticate-bot-file-requests)

## Intake, permissions and conversation references

Use a short durable intake path for authenticated activities. Scope a message's opaque Activity ID to its verified app, tenant, installation and conversation. Commit acceptance, a repeat, a conflict or refusal before responding successfully. A commit failure returns the appropriate retryable response. Complete the ordinary receipt within Teams' 15-second activity response budget. Keep model work, media retrieval and slow lookups off that response path. Apply explicit expiry and identity to invokes and lifecycle events. Suppress self and system events as ordinary input. Recover accepted work and exact replies from native receipts. Connector retries can repeat an activity. Report an observed intake gap if it cannot be replayed through this interface. [Microsoft Teams activity handlers and retries](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/bot-concepts) · [Gateway intake and recovery](ADAPTER_CONTRACT.md#intake-ordering-and-execution-recovery)

- **Identity and installation.** Treat Entra object IDs under their verified directory tenant, Teams per-bot user IDs, and Teams resource IDs as distinct namespaces. Associate them only with verified activity and roster evidence. Scope guest access to the verified resource installation and the actor's available verified identity. Check user, membership and conversation grants before admission, control, context reads and delivery. Installation events, membership changes and resource consent updates refresh or revoke only the affected grants. Resolve ambiguous lifecycle order against current installation evidence. A team install grants access to private and shared channels only where the specific channel supports and verifies its own installation and consent. [Teams conversation references](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/send-proactive-messages#get-the-conversation-id) · [Teams resource-specific consent](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/resource-specific-consent)
- **Chat and mention policy.** Authorized personal chats can start work without a mention and can use native DM pairing if enabled. Group chats and channels default to an authenticated mention of this app or a verified reply to one of this app's confirmed activities. Use structured mention identities and strip the bot's matching markup before command recognition. Installations may explicitly enable free response using current resource-specific consent (RSC) for the exact team or chat. `ChannelMessage.Read.Group` and `ChatMessage.Read.Chat` widen delivery of visible events. Mercury still applies the route and actor's admission policy before fetching any attachment or history. Persist shared or participant-isolated session bindings per policy. [Hermes Teams mention behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/teams.md#how-the-bot-responds) · [Microsoft Teams message consent](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/channel-messages-with-rsc)
- **Exact destination.** Preserve the authenticated Connector conversation reference, including cloud, app, tenant, installation, service endpoint, chat or team and channel, and root or reply anchor where applicable. Use the verified activity or provider binding for channel thread roots. Treat conversation and activity IDs as opaque path parameters. Personal and group chats use supported flat or quoted replies. A channel reply remains under its verified thread. Store the reference independent of session sharing. A refreshed endpoint may be used for new dispatch only after it is verified for the same authorized installation and destination. An existing uncertain send remains bound to its original attempt. [Microsoft Teams proactive message routing](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/send-proactive-messages) · [Microsoft Connector REST reference](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-api-reference?view=azure-bot-service-4.0)

## Commands and Adaptive Cards

Use native session and model selection, skills, queue, steering, stop, status, approvals, clarification and proactive target setup under the same grants as other clients. Use Adaptive Card `Action.Execute` approval prompts at the version verified for Teams. Offer allow once, allow for the session, durable allow, and deny according to the native approval descriptor. Include a bounded preview and expiry. Use opaque scoped action IDs in the card. Bind each action to the app, tenant, installation, exact conversation and original card, authorized actor or role, request, allowed choice, expiry and native execution generation. Use the sender from the authenticated invoke. A card field cannot designate an actor, session or route. Use scoped text for controls where a native card is unavailable. [Hermes Teams approval cards](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/teams.md#interactive-approval-cards) · [Universal Action Model](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model)

Answer `adaptiveCard/action` through the native durable control path, with a five-second implementation budget for validating the action, committing the result and returning a scoped response. Commit the decision before returning a resolved card or scoped feedback. A repeated invocation reads its recorded disposition under current authority, even when the earlier HTTP response was lost. A wrong actor or stale request cannot approve and gets feedback only in the permitted audience. An invoke response can replace the card for the invoking client. When shared card retirement is required, update the exact confirmed original activity through its own leased outbox effect. Card presentation and native decisions have independent receipts. Expired presentation or missing permission to update a card leaves the recorded native decision intact. [Microsoft Universal Actions response format](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model) · [Hermes Teams card handler](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/teams/adapter.py#L644)

## Attachments and voice

**Authorized intake.** Stage valid inline images, documents, audio and video through profile-scoped artifacts, including media-only messages. Separate Connector-backed media from Teams personal-file handles and authorized Graph-backed files. Fetch Connector attachments with a Connector token at the verified origin. Bind personal-file handles to the source activity, file identity, storage host and verified file tenant. Bound actual bytes, content type and time, check every new destination before following a redirect, and keep secrets and MIME handling under the scoped media boundary. A gated chat or unavailable permission creates no download or transcription. A short-lived handle that has expired yields a durable unavailable attachment state. Use the profile's transcription and synthesis for voice workflows. [Hermes Teams media handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/teams/adapter.py#L478) · [Teams files API](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/bots-filesv4)

**Authenticated personal files.** Target Microsoft's authenticated `downloadUrl` and `uploadUrl` flow. Use the bot app ID with a certificate or another supported secretless credential to get the file token for the exact verified storage host. Use the verified file tenant from the attachment or upload metadata, with the activity tenant used when the file tenant is absent. Require an approved tenant and host binding before issuing or sending that token. Declare `supportsFiles` for personal chat. The manifest declares `File.ReadSelected.User` for downloads or `File.ReadWriteSelected.User` for uploads when Microsoft starts accepting these permissions on January 15, 2027. Microsoft ends reliance on the temporary URL authorization on March 1, 2027. Generate and verify the package against the capability available at deployment time. Mercury uses authenticated transfer throughout. [Microsoft file authentication transition](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/bots-filesv4)

**Outbound media and consent.** Send supported inline media from scoped artifacts within the serialized Teams activity budget. Use an authorized file attachment or storage reference when larger audio, video or documents require it. For a personal file, publish a consent card that binds the exact artifact, app, conversation, requester or recipient, and expiry. Commit `fileConsent/invoke` acceptance or decline before acknowledging it. An accepted callback authorizes the named upload under the current account and storage binding. Save the upload result before posting the file-information card or native attachment. For group or channel files, use a Teams-supported authorized attachment or a separately authorized Graph and OneDrive or SharePoint reference under that exact audience. Personal file consent cannot authorize a group upload. Missing permissions produce a typed unavailable attachment outcome. Preserve captions and thread anchors and keep the artifact available through the native owner. [Teams file consent and storage](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/bots-filesv4#send-files) · [Microsoft 365 Agents file consent](https://learn.microsoft.com/en-us/microsoft-365/agents-sdk/teams/teams-files)

## Delivery, recovery and meeting-summary results

- **Replies and proactive results.** Render supported Teams text and card content with sanitized formatting and bounded chunks, accounting for JSON, card and attachment encoding overhead. Treat typing as expiring progress and send the final committed result through the outbox. Reply using the verified activity and conversation reference. Routines, completed webhooks, background runs and authorized manual sends use a verified installed home destination or exact thread. An installed personal recipient or channel can be provisioned through the supported proactive conversation or thread operation under the shared host lease. Save the confirmed reference before dependent sends. An unknown provision or missing installation holds dependent work. [Hermes Teams send path](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/teams/adapter.py#L735) · [Microsoft Teams proactive sends](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/send-proactive-messages)
- **Effect evidence.** Record the exact app, tenant, endpoint, destination, anchor and returned activity ID for accepted sends. Honor `Retry-After` and cooldowns in the applicable app, tenant or conversation scope. An ambiguous Connector POST, upload, card update or provisioning claim stays uncertain until exact evidence or owner disposition. A known unsupported reply operation can use an approved flat chat plan after definite non-acceptance and only within the same authorized audience. A failed channel-thread reply cannot become a channel-wide post. Scope any installation, caller or permission refusal to its binding and maintain unrelated progress. [Microsoft Connector REST reference](https://learn.microsoft.com/en-us/azure/bot-service/rest-api/bot-framework-rest-connector-api-reference?view=azure-bot-service-4.0) · [Microsoft Teams rate limits](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/rate-limit)
- **Meeting-summary delivery.** Accept a committed summary as an outbound intent from a separate producer under the same outbox. Carry the producer receipt and source audience authorization. Default to an explicitly installed Bot Connector target. A configured Graph summary route uses the exact chat, channel or thread under a separate authorized Graph principal and endpoint grant. Support delegated `ChatMessage.Send` or `ChannelMessage.Send` for the respective supported endpoints. An app-only route needs a Microsoft-supported resource-specific grant for that operation and live proof against the actual target. Ordinary summaries never use migration permissions or broad Graph rights as a send substitute. Graph results have their own message IDs and sending identity, with no automatic switch from an uncertain Connector send. [Hermes meeting summary writer](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/teams/summary_writer.py) · [Microsoft Graph chat send](https://learn.microsoft.com/en-us/graph/api/chat-post-messages?view=graph-rest-1.0) · [Microsoft Graph channel send](https://learn.microsoft.com/en-us/graph/api/channel-post-messages?view=graph-rest-1.0) · [Teams resource-specific consent](https://learn.microsoft.com/en-us/microsoftteams/platform/graph-api/rsc/resource-specific-consent)

## Implementation and acceptance

| Work | Depends on | Ready when |
| --- | --- | --- |
| App package, signed ingress and account binding | Shared stock-plugin gate and Matrix live acceptance | The current Teams package installs and the receiver verifies app, tenant, audience and service endpoint. Bad signatures and wrong registration or installation are refused. |
| Durable intake and routing | Verified receiver and install evidence | Personal and group chat and channel-thread input are durably deduplicated. Mention policy and consent are enforced. Stored conversation references recover after restart and stay bound to the correct tenant and destination. |
| Adaptive Cards, files and delivery | Verified route and shared controls, media and outbox | Approval responds in budget after durable decision. Authenticated downloads, personal file consent, scoped producer sends and unknown outbox effects recover through the transport suite. |
| Live acceptance | Completed transport suite | A configured tenant and real Teams clients prove all baseline workflows. Private or shared channels, Graph delivery, and additional cloud capabilities are advertised only after live proof for their enabled scope. |

Use a scripted Connector, OpenID key service, Entra token service and file or Graph endpoint behind the production adapter. Exercise the native profile owner and persistent storage with a deterministic model. Run the Teams transport suite, shared polling and push conformance, and `cargo test --locked --workspace`. [Gateway owner tests](tests/owner.rs) · [Hermes Teams fixtures](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/gateway/test_teams.py)

| Transport case | Evidence |
| --- | --- |
| Authentication and installation | Exercise signing key rollover, invalid issuer or audience, a mismatched tenant or service URL, two profile bindings and stale receiver writes. Remove an installation or consent after queueing and verify the affected route is refused. |
| Duplicate intake and exact routing | Lose the response after durable intake and replay the activity. Reopen before native claim and before reply. Suppress unmentioned group events before media reads, resolve a verified bot reply, and deliver to the original thread after restart. |
| Native controls and files | Replay an approval and file-consent callback, including wrong actor, foreign installation, expiry and lost response. Recover a staged upload without repeating publication. Verify file-host token and tenant isolation, denied attachments, and a stable private decision after card presentation fails. |
| Proactive and unclear outcomes | Recover a confirmed home reference and reply anchor. Test definite rate limiting, a missing send response, a missing provisioning response and a delayed summary. Prove that only the affected destination holds and an unverified audience change cannot release its result. |

For live acceptance, install the app in personal, group and team scopes in a controlled tenant. Complete a DM, a mentioned group reply and a channel-thread exchange. Under active RSC, verify that an unaddressed message is refused by policy before file access, then exercise explicit free response. Use a real Adaptive Card for a native approval, an authenticated personal file download and consent upload, and a voice or media round trip. Restart between intake and reply, and deliver a routine and summary-shaped result through the saved target after restart. Record the app schema, cloud, connection and permission configuration used. Verify any optional Graph file or summary route with its own live credential and audience. ## Scope

Exclude the archived Bot Framework SDK and emulator, retired Office 365 Connector webhooks, legacy multi-tenant bot registration, and temporary unauthenticated file URL fallback. Meeting Graph subscriptions, transcripts, recordings and summarization belong to the separate meeting pipeline. Teams calling, live response streaming, and unrelated Power Automate workflows are outside this stock adapter's Hermes parity scope. Desktop UI remains deferred.
