# WeCom stock plugin implementation spec

Bundle WeCom as one Rust stock plugin with two adapter registrations. `wecom` serves WeCom AI Bots over WebSocket. `wecom_callback` serves self-built enterprise apps through encrypted HTTP callbacks. Start after DingTalk and the shared contract pass their gates. Qualify both modes separately before Weixin starts. Each has its own setup, identity, lease, policies, delivery limits and acceptance. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [DingTalk spec](DINGTALK_ADAPTER_SPEC.md) · [Hermes WeCom manifest](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/wecom/plugin.yaml) · [Next adapter, Weixin](WEIXIN_ADAPTER_SPEC.md)

## Registration and ownership

Put the factories and wire clients in `hermes-gateway::messaging::wecom`, using separate modules for AI Bot and Callback. Keep transport-specific encryption, protocol requests and rendering inside them. Reuse the profile owner's credential storage, leases, durable intake, session policy, command authority, attachments and outbox. Settings and health identify the mode and verified bot or application unambiguously. Verify same-account rotation before preserving a live route. Exposure on one mode grants no permission in the other. [Mercury adapter types](src/messaging/types.rs)

## AI Bot WebSocket

**Setup and lifecycle.** Accept owner-configured bot ID and secret and support the documented scan-to-create path through a private expiring setup session. Use the qualified TLS endpoint, `aibot_subscribe` and verified acknowledgement, application heartbeat and reconnect with backoff. Fence old connections and outstanding request generations. Keep a ready socket distinct from verified receive continuity. Bot messages and chat IDs are scoped under that verified bot. [WeCom official AI Bot SDK](https://github.com/WecomTeam/aibot-node-sdk) · [Hermes WeCom setup](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/wecom.md)

**Intake and access.** Verify bounded callback frames against the connection and normalize message ID, actor, direct or group chat, quote and source request ID. Persist recoverable staged input and exact disposition. Dedup by verified bot and message ID, independent of the provider `req_id` and socket. Preserve transport events and receipts without admitting turns. Reconnect drains local staged inputs and reports any unverified gap. Apply DM allowlist or pairing and group policy, then per-group sender overrides and authorized mention or free response. Do not let a chat or display label identify a different actor. Bind native commands and text controls to the correct route and generation. [Hermes WeCom transport and identity](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/wecom/adapter.py#L285)

**Replies and streaming.** Bind each response to its original `req_id`, recipient, expiry and connection context. Prepare Markdown or native `stream` frames with stable stream identity per native turn. The reply window is finite. A configured keepalive stays within the verified provider cadence and refresh evidence. Persist and order streaming edits and finalization. Serialize frames that share a request ID. After a timeout, a subsequent ack cannot confirm a later frame without exact evidence. Restart reuses an unfinished stream only if the provider context and earlier effects can be verified. Use proactive sends for separately authorized delivery and as final fallback after known reply ineligibility or non-acceptance, with the same intended audience. Hold an ambiguous final instead of sending a second final through the other path. A visible partial preview has its own receipt and does not imply final acceptance. [Hermes stream and same-request ack handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/wecom/streaming.py) · [Hermes WeCom reply modes](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/wecom.md#reply-mode-responses)

**Media and proactive sends.** Preserve mixed messages, approved quote attachments, signed download origins and provider voice transcript. Decrypt authorized media through the verified provider scheme, validating key, size and padding without exposing key material. Upload native images, videos, AMR voice and generic files using init, bounded indexed chunks and finalization. Persist the upload ID, verified chunk receipts and completed media ID. Revalidate any expiring reference before publication or retry. Use the qualified provider limits, including Hermes's 10 MB image/video, 2 MB native voice and 20 MB absolute file budgets. Downgrade incompatible media to file within that bound. Use the permitted native reply or explicit proactive route for media and captions. Bind scheduled output to a verified home chat. [Hermes WeCom media handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/wecom/media.py)

## Self-built app Callback

**Setup and receiver.** Bind each application to corporate ID, agent ID, callback verification token, EncodingAESKey, app secret and designated HTTPS receiver. Verify application access and current visible user scope. Allow multiple corporate installations and apps, with an app-specific slot or a uniquely verified match at a shared receiver. Validate the URL-verification challenge and bounded callback envelope under WeCom's signature and freshness rules before trusting the decrypted identity. Enforce authenticated receiver ID and verified agent ID for events, with exact slot binding where the provider omits the agent field in a challenge. Reject mismatched or ambiguous candidates. Parse hardened XML with external entities disabled. Acknowledge valid retryable delivery only after durable disposition, with an empty provider receipt separate from the eventual user reply. [Hermes Callback setup and crypto](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/wecom-callback.md) · [Hermes Callback verifier](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/wecom/wecom_crypto.py)

**Text and authorization.** Use corporate ID, agent ID and authenticated user ID as the app DM route. Bind `MsgId` or a documented authenticated event identity to a durable receipt. A timestamp plus user ID alone may collide. Handle app entry and subscription lifecycle as events, and unsupported content as typed outcomes. Support the app sidebar text DM and text commands, approvals and clarification under app/user policy. An identical user ID at another app or corporation creates no shared credential, route or receipt. Verify an audience and capability before each effect. [Hermes Callback event and routing code](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/wecom/callback_adapter.py#L238)

**App delivery.** Obtain and refresh an access token under the selected corporate app binding, then use WeCom `message/send` for final replies and approved proactive output. Split at the qualified text limit of 2,048 UTF-8 bytes without breaking characters. Check application errors and invalid recipients alongside HTTP status. Retain the original sender route as the destination and use the native outbox across restarts. Record exact returned effect evidence where available. A lost send with no exact proof remains uncertain. The reference Callback adapter accepts and sends text. Do not advertise bot-mode groups, streams, typing or media based on the generic WeCom presentation hint. [Hermes Callback limitations](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/wecom-callback.md#limitations) · [Hermes Callback send path](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/wecom/callback_adapter.py#L190)

## Implementation and acceptance

| Step | Prerequisite | Evidence |
| --- | --- | --- |
| AI Bot transport | DingTalk live acceptance and expanded shared gate | Verified leased WebSocket connection, intake, DM and group policy, native stream and media outbox. |
| AI Bot live acceptance | AI Bot transport suite | Real private and group chats, quoted media, long turn, stream recovery and scheduled delivery. |
| Callback transport | AI Bot live acceptance | Signed and encrypted challenge and event fixtures, durable retries, corporate/app isolation and text delivery. |
| Callback live acceptance | Callback transport and shared conformance | Current self-built app setups prove authorized sidebar DMs, delivered replies, proactive output and isolated restart. |

Use scripted WebSocket and HTTP transports with disposable profile stores and the production adapters. Exercise repeated logical messages under different sockets and request IDs, delayed stream acks, expiry before a long-turn final, uncertain final followed by fallback request, segmented media failure, forged challenge and XML, two apps sharing a corporate user name, and callback response loss after intake commit. Test native commands and subsequent result release with a deterministic provider. Run shared conformance and `cargo test --locked --workspace`. Record provider releases, enabled modes and exact live evidence, including two independently bound Callback applications and a denied cross-app operation.
