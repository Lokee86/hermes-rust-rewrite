# QQ Bot stock plugin implementation spec

Register QQ Bot as a bundled Rust adapter with key `qqbot`. Start after Weixin and the shared gate. Serve an official QQ bot's eligible private C2C chats, QQ groups, guild text channels and guild DMs over the provider Gateway and REST API. Cover the reply modes still available through QQ's current API. Tencent's send documentation explicitly retired general proactive push on April 21, 2025. A configured Hermes home label alone therefore grants no scheduled push. ## Connection and durable intake

Put the factory and wire client in `hermes-gateway::messaging::qqbot`. Bind each official App ID, secret, qualified sandbox or production endpoint, bot identity and approved intents privately to its profile. Support the developer-portal setup path and safe App ID/secret enrollment. Verify token access and Gateway identity before marking ready. Keep every token cache and transport generation app- and environment-scoped. Use current QQBot authentication, documented Gateway discovery, Hello, heartbeat and acknowledgement. Subscribe only to the scopes needed for the enabled C2C, group-at, guild, guild DM and interaction paths. [Mercury adapter types](src/messaging/types.rs) · [Tencent Gateway protocol](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/dev-prepare/interface-framework/event-emit.md)

Durably record the session ID and highest safe dispatch sequence under the app and shard. Distinguish connection heartbeat state from the durable resume position. Stage each verified dispatch before advancing the safe sequence. Resume through the provider's session recovery with that position. A non-resumable session, replaced shard or unfilled interval reports a gap before re-identifying. Scope dispatch IDs, message IDs and interaction IDs by application and verified resource kind. Merge provider-delivered copies and hold conflicting reuse. No native admission for own echoes, membership updates, audits or unrelated interactions. [Hermes identify and resume](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/qqbot/adapter.py#L458)

## Native routes and controls

Use exact typed routing for C2C `user_openid`, group `group_openid` and `member_openid`, guild and channel IDs, and the authenticated guild DM conversation and author. An OpenID in one application or namespace grants no other route. Apply DM, guild/channel/group and participant policy independently, then honor group-at and granted responder behavior. Keep the immutable reply target and source identifiers separate from a shared or per-user conversation binding. Preserve supported quote context after policy. Recheck access before protected reads, native claim, interaction and delivery. [Hermes QQ route mapping](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/qqbot/adapter.py#L741)

Expose text commands, clarification and approvals through the native owner. For qualified surfaces render Markdown keyboards for the published control capabilities, including approval and update confirmation. Bind a provider interaction to its opaque action, original prompt/request, bot app, verified operator and exact destination. Preserve expiry and execution generation, and commit the native action disposition before acknowledging success. Repeat interactions return the same decision or refusal. A callback that only carries a session label cannot affect any pending control. Surface text interaction where keyboard permissions or the scene lack an interactive capability. [Hermes QQ keyboard code](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/qqbot/keyboards.py)

## Replies, attachments and eligibility

Use the official REST endpoint for the exact scene. Account for both HTTP and provider application status. Render plain text or configured authorized Markdown and preserve the published formatting, approved URL and reply limits. Reserve the applicable passive `msg_id` or supported `event_id` and a stable `msg_seq` where documented before dispatch. Keep each reply's provider budget and deadline scoped to its input and scene. Qualify provider time and count by app and route because examples and live limits can differ. Do not spend an uncertain slot again under a new sequence. A duplicate-rejection code is not itself a returned message ID or proof of user delivery. Use exact association or the qualified provider guarantee to settle the attempt. General unsolicited push and token-free fallback are out of scope. A scheduled or manual result can use a currently authorized event-bound reply only when the provider explicitly permits that effect. Otherwise the outbox reports that delivery is unavailable or expired. [Tencent send rules and identifiers](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/server-inter/message/send-receive/send.md)

Stage authorized images, audio, video and documents from the exact inbound route. Use valid provider ASR text for voice where available, otherwise use profile transcription. Qualify receiving limits, MIME and origin; cache only bounded content. For supported C2C and group routes, prepare uploaded media without publishing, retain QQ's `file_info`, then publish a native media message under a reply grant. Qualify remote-URL upload for permitted sources and segmented uploads for bounded local media. Persist upload allocation, confirmed parts and final reference. Honor file size and quota errors. Guild media sends, typing and interactive rendering are separately advertised only where the current app and scene qualify them. Provide a typed presentation limit instead of shifting the audience. [Hermes QQ media delivery](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/qqbot/adapter.py#L1553) · [Hermes media upload fixtures](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/gateway/test_qqbot.py)

## Implementation and acceptance

| Step | Prerequisite | Evidence |
| --- | --- | --- |
| Verified Gateway and resume | Shared gate and Weixin live acceptance | App, environment and scope verification, durable committed sequence, replay and explicit gap handling. |
| Scenes and native effects | Durable dispatch | Correct C2C/group/guild routes, exact reply grants, command and keyboard receipts and qualified media. |
| Live acceptance | Transport and shared conformance | Real QQ client and qualified app prove enabled routes, media, controls and recovery within current provider limits. |

Drive scripted Gateway and REST fixtures through the production adapter and Mercury owner. Exercise reconnect after receipt commit and before advancing a batch, invalid-session rebuild, equal local IDs across apps and scenes, denied guild DM actor, forged and repeated keyboard actions, provider approval of Markdown, expired and consumed passive replies, duplicate sequence rejection, uploaded-but-unpublished media and interrupted sends. Run shared conformance and `cargo test --locked --workspace`. Use a qualified QQ app to prove C2C, allowed group mention, guild messages and guild DMs wherever approved. Exercise text approval, eligible keyboard, voice and uploaded media, rate/expiry refusal and recovery after a device or process reconnect. Record provider grants and quota behavior before advertising each scene.
