# Google Chat stock plugin implementation spec

Register Google Chat as a bundled Rust adapter with platform key `google_chat`. Start after Mattermost and the expanded shared contract pass their gates. A headless Mercury profile serves a Google Chat app in DMs, group conversations and spaces, preserves reply placement across restart, carries native controls, and delivers files with scoped user consent. Hermes v0.23.4's manifest and adapter support authenticated HTTP callbacks and Cloud Pub/Sub pull. Qualify both. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [Mattermost spec](MATTERMOST_ADAPTER_SPEC.md) · [Hermes Google Chat manifest](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/google_chat/plugin.yaml)

## Registration and connection

Put the factory and Google wire clients in `hermes-gateway::messaging::google_chat`. The adapter owns Chat event parsing, Pub/Sub intake, Google token exchange and Chat REST rendering. The profile owner supplies leases, private credential references, durable intake, routing, commands, delegated grants, artifacts and the outbox. Store the configured Google project and app binding, app service account and exactly one intake mode per logical app. Verify setup before leasing it. A transport change fences the old intake and retains existing Chat resource identities and receipts. Explicitly bound workload credentials may replace a service-account key. Do not discover ambient credentials belonging to another profile. Use Chat app authentication for regular REST sends. [Mercury adapter seam](src/messaging/types.rs) · [Chat app authentication](https://developers.google.com/workspace/chat/authenticate-authorize-chat-app)

- **HTTP.** Use the gateway listener for a dedicated HTTPS receiver slot. Qualify Google's endpoint-URL audience mode. Validate signature, issuer, lifetime, exact audience and the configured service-account identity for the selected Chat app type using Google's current keys. For a shared Google sender, allocate a distinct endpoint audience per app installation and verify the configured installation evidence before activating it. Reject unknown slots, unauthenticated payloads and oversized bodies before any dispatch. Acknowledge quickly after the event or a recoverable handoff is durable. Use Chat REST for delayed results. A retry after receiver timeout can read the existing disposition. [Google Chat request verification](https://developers.google.com/workspace/chat/verify-requests-from-chat) · [Hermes HTTP intake](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/google_chat/adapter.py#L874)
- **Pub/Sub.** Verify the fully qualified project, topic and pull subscription as one binding. Give only the configured publishing identity publish access to the topic and grant the installation's subscriber the minimum required access on its subscription. Bound in-flight count and bytes. Use leased per-delivery acknowledgements. Extend the deadline only during bounded preparation, acknowledge after durable disposition, and let an uncommitted item redeliver. Durable staging is sufficient for acknowledgement when the host can complete preparation later. A fresh ack ID or subscriber reconnect does not create a new logical Chat input. Report lost retention, unexpected subscription recreation and dead-lettering when detectable. Pub/Sub does not provide global event order by default. Preserve observed order per route and keep slow routes independent. [Chat Pub/Sub setup](https://developers.google.com/workspace/chat/quickstart/pub-sub) · [Pub/Sub lease management](https://docs.cloud.google.com/pubsub/docs/lease-management)

## Intake, routing and controls

Normalize verified native Chat interaction events and matching supported Workspace add-on envelopes. A message resource name identifies one logical input under the bound app, even when two transport envelopes differ. The transport envelope identity allows duplicate acknowledgement and malformed-item disposition. Preserve sender resource ID and exact space and thread resource names from authenticated fields. A differing payload for the same immutable message is a conflict or classified edit. Never create a second turn for an edited copy, transport retry, own app output or repeated system event. Handle install and removal as membership updates, recheck app and actor access on protected reads, claim, controls and send. Treat verified emails as enrollment aliases for `users/{id}`; labels and message-body emails confer no rights. Accept the current DM and authorized mention or command workflows, with explicit policy for shared rooms. [Chat interaction events](https://developers.google.com/workspace/chat/api/reference/rest/v1/Event) · [Hermes Google Chat routing](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/google_chat/adapter.py#L941)

Persist the DM main conversation and explicit DM side-thread binding separately. Chat can assign a thread resource even to an ordinary top-level DM. Preserve Hermes's ordinary DM flow and isolate a verified continuation of an existing thread. Use provider topology where available, with a durable record of observed roots and authored replies when the deployment uses the seen-thread heuristic. Redelivery cannot advance that record. A named-space thread retains its exact source thread across progress, chunks, controls and user-attributed files. Send to an existing thread with `REPLY_MESSAGE_OR_FAIL`. If the thread disappears, hold the destination and report the result. Operator-configured home destinations require verified space or thread access. [Chat create and reply modes](https://developers.google.com/workspace/chat/api/reference/rest/v1/spaces.messages/create)

Map configured provider command IDs and typed commands to the native command descriptors. Keep an app command tied to the verified actor and space. Use scoped text responses for approvals and open-ended clarification. Render fixed-choice clarification as a Cards v2 prompt where the tested interaction channel carries a verified `CARD_CLICKED` event. Bind its opaque action and choice to the posted message, actor, route, expiry and native execution generation. Acknowledge an already committed click without executing it again. Include a typed-answer choice. Hermes v0.23.4's default Pub/Sub handler acknowledges widget events without dispatching them, so use text clarification for that mode unless actual Google delivery of the supported callback can pass the same gate. [Hermes card and text behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/google_chat.md#clarify-questions-as-interactive-cards) · [Hermes Pub/Sub handler](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/google_chat/adapter.py#L829)

## Delivery and files

Render supported Chat text formatting and split at a conservative 4,000 characters and the provider byte limit. An optional working marker is a visible message. Persist its accepted resource ID before editing it into the first final part. Scope every edit and cleanup to that gateway-owned message. Subsequent chunks and attachments use ordered delivery. Prepare a stable `requestId` and provider-valid `client-` message ID for each create where the API supports them. Keep the body, effective author and destination immutable. After an ambiguous response retrieve the known custom ID and verify the exact effect, or retransmit only under a provider-qualified replay guarantee. The API's request deduplication has no assumed indefinite lifetime. Honor quota deadlines and hold ambiguous operations lacking exact evidence. Maintain authorized home routes for scheduled, webhook and manual results. [Chat message creation](https://developers.google.com/workspace/chat/api/reference/rest/v1/spaces.messages/create) · [Chat message edit](https://developers.google.com/workspace/chat/api/reference/rest/v1/spaces.messages.patch)

Stage native attachments after the actor and route pass policy. Resolve attachment data through Chat's scoped media API or its supported authenticated download reference. Validate Google origin before a credential-bearing fetch, including redirects. Keep inbound media types and file-only messages, use shared transcription where audio is available, and offer permitted link or format fallbacks. Native Chat attachments use user authentication. Expose `/setup-files` status, enrollment and revocation in the user's verified DM. Complete authorization through the profile's private OAuth redirect flow with expiring state, PKCE and verified user identity, requesting Chat's `chat.messages.create` scope and the identity claims needed for the binding. Never collect a code in chat. Persist a grant scoped to the installation and actor. Store the initiating actor on the request and effect. Bind the uploaded `attachmentDataRef` to that user, artifact and space, then create its attachment message with the same authorized identity under current policy. Show that send as user-attributed. Without the exact grant, send a scoped setup or unavailable notice. No shared author token or cross-user fallback. No native voice-note UI is required. [Hermes per-user file flow](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/google_chat.md#step-10-native-attachment-delivery-optional) · [Chat upload API](https://developers.google.com/workspace/chat/api/reference/rest/v1/media/upload) · [Chat media download API](https://developers.google.com/workspace/chat/api/reference/rest/v1/media/download)

## Implementation and acceptance

| Step | Prerequisite | Evidence |
| --- | --- | --- |
| Registration and intake | Shared gate and Mattermost live acceptance | Verified app bindings and both intake transports stage real event shapes, survive pause or restart and isolate profiles. |
| Sessions, controls and delivery | Durable intake | Authorized DM and space/thread turns, card and text controls, progress edits and recoverable ordered replies use native authority. |
| Files and proactive delivery | Verified actor and outbox | Revocable per-user enrollment, correctly attributed attachment sends and authorized home delivery work under restart and revocation. |
| Live acceptance | Completed transport checks and shared conformance | Current Workspace test installs prove both intake modes, threaded routing, clarification, attachments and recovery. |

Use scripted Google REST, signed HTTP fixtures and a controllable Pub/Sub subscriber through the production adapter and real Mercury profile owner. Cover authentication and cross-app rejection, process death before receipt commit and after commit before ack, redelivery with a new ack ID, duplicate logical messages across transport change, DM root versus side thread, a removed space, a forged or stale card click, uncertain create and marker recovery, and two users authorizing or revoking files while sharing a space. Run the shared polling and push conformance and `cargo test --locked --workspace`. In live testing, use isolated configured Chat apps or controlled transport reconfiguration and real clients. Exercise an authorized and denied actor, DM, named-space thread and command, a fixed-choice prompt in HTTP mode, file read and consented upload, and a scheduled reply after restart. Record qualified callback shapes, consent and delivery evidence. ## Scope

Exclude generic relay envelopes that synthesize actor identity, standalone senders and the legacy shared Google user token. Arbitrary space administration, Drive access, and Desktop UI are outside this messaging plugin. [Backend parity scope](../../BACKEND_PARITY_PLAN.md#scope)
