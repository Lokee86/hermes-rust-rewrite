# DingTalk stock plugin implementation spec

Register DingTalk as a bundled Rust adapter with platform key `dingtalk`. Start after Feishu/Lark and the shared contract pass their gates. A headless installed enterprise robot serves authorized DMs and groups through DingTalk Stream Mode, processes attachments, and uses session Markdown or configured AI Cards for replies. Keep current approved scheduled delivery under the same gateway. ## Registration and durable Stream Mode

Put the factory and wire client in `hermes-gateway::messaging::dingtalk`. Configure and verify an enterprise application ID, client credential, corporation and robot code. Bind the Stream Mode connection and REST token to that installation and profile. Use DingTalk's authenticated connection discovery, WebSocket system messages and chatbot callback topic. Restrict discovery URLs and token-bearing requests to qualified provider origins. Preserve one leased connection per installation, fence old sockets on rotation, and expose handshake, heartbeat, authorization and degraded capability status. Rebuild disconnected sockets with bounded backoff and a stable-period reset. Repeated credential denial requires owner attention. [Mercury adapter types](src/messaging/types.rs) · [Official DingTalk Stream SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-python)

Validate bounded callback envelopes and match their scope before interpreting content. Distinguish the Stream callback acknowledgement ID from the chatbot message ID. Bind each logical message to the verified robot and corporation, with immutable conversation and sender evidence. Persist an event disposition or admitted handoff before sending a success acknowledgement. Return a retryable disposition when a transient write fails and allow a repeated callback to read the first outcome. Keep model work and download resolution off the acknowledgement path. A reconnect resumes durable local preparation. Stream reconnect does not prove provider replay. Explicitly surface any unfilled intake period when a resume cannot be verified. [DingTalk Stream frame handling](https://github.com/open-dingtalk/dingtalk-stream-sdk-python/blob/main/dingtalk_stream/frames.py) · [Hermes DingTalk callback](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/dingtalk/adapter.py#L723)

## Chats, controls and media

Use verified conversation type, conversation ID and authenticated sender IDs. A directory/staff ID has authority only within its verified corporation and app. Isolate DM and group participant sessions by default with explicit sharing policy. Apply user and room grants before group mention, configured textual wake patterns or open response. A message's `sessionWebhook` and expiry are secret-bearing reply evidence. Bind them to its verified conversation, installation, source event and allowed operation. Keep them out of prompts and diagnostics. An authorized later event can establish a fresh grant. A duplicate or a message from another actor or destination cannot extend or retarget the original effect. Recheck membership and grant validity before claim and delivery. [Hermes DingTalk admission and reply address](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/dingtalk/adapter.py#L459)

Expose supported typed commands, approvals, clarification, queue and stop as text via the native authority. A displayed card is presentation unless a separately qualified callback has native action support. Optional Thinking/Done reactions attach only to an authorized original message and follow its durable lifecycle. Track source IDs even when two messages in the same chat overlap. Suppress reactions for denied or duplicate messages. Render brief progress according to configured display modes and provider capabilities. [Hermes DingTalk reactions and display](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/dingtalk.md#emoji-reactions)

Normalize text, rich text and recognized incoming card summaries. Preserve embedded media and use scoped download-code resolution for images, files, audio and video. Stage bytes only after authorization. Pin request and temporary download origins, enforce size and type limits, and transcribe authorized audio where supported. A session Markdown reply can render permitted remote images or link presentations. Local attachment upload is unavailable through that reply endpoint. Report a typed capability limit rather than exposing local paths. [Hermes DingTalk media normalization](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/dingtalk/inbound.py)

## Delivery and recovery

**Session Markdown.** Use the exact admitted reply route and applicable deadline. Persist bounded Markdown parts and honor the reference 20,000-character budget plus any provider byte limit. Confirm provider acceptance from its response body as well as HTTP status. An absent provider message ID does not justify inventing one for reconciliation. Retry with current authorization after a definitive transient non-acceptance. An ambiguous result holds the part. An expired or missing grant blocks the original reply. Resumption through a newer grant is allowed only if the provider permits reusing it for that same verified destination and policy still permits the intended effect. [Hermes session webhook handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/dingtalk/adapter.py#L503)

**AI Cards.** Qualify the configured template and permission with real recipients. Persist the card's `outTrackId` before creation, bind its group or robot-private delivery space and record creation, publication, full streaming revisions and finalization as distinct effects. Keep each revision's identifier and immutable payload. Finalize only the confirmed published card for that turn. Serialize revision sends and ignore stale updates after terminal confirmation. Resume only effects with proven acceptance state or a qualified replay guarantee. A card ID by itself is correlation evidence. Use Markdown fallback only after a definite pre-publication failure when there is no ambiguous visible card and the session grant remains usable. [DingTalk card publishing reference](https://github.com/open-dingtalk/dingtalk-stream-sdk-python/blob/main/dingtalk_stream/card_replier.py) · [Hermes streaming card operations](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/dingtalk/adapter.py#L573)

**Unattended delivery.** Provision an explicitly approved home target on the bound enterprise app robot through DingTalk's current OpenAPI. Verify the application token scope, robot identity and exact eligible DM user or installed group before enabling the target. Keep eligibility distinct from the transient session URL, and persist the provider's effect evidence under the native outbox. A deployment without the required permission reports that capability unavailable. [DingTalk application robot message API](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/appbot/reply/)
