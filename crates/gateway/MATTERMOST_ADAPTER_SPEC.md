# Mattermost stock plugin implementation spec

Register Mattermost as a bundled Rust adapter with platform key `mattermost`. Start after Microsoft Teams passes live acceptance and the expanded shared stock-plugin contract passes conformance. A headless Mercury profile can work in authorized DMs, group messages, public and private channels and threads on a supported Mattermost server. It can exchange files, accept native session controls, deliver unattended results, and reopen committed work after a disconnect or restart. The reference is the Hermes v0.23.4 bundled adapter and Mattermost's v4 API. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [Teams spec](TEAMS_ADAPTER_SPEC.md) · [Hermes Mattermost guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/mattermost.md) · [Mattermost v4 API](https://api.mattermost.com/)

## Registration and connection

Put the factory and wire client in `hermes-gateway::messaging::mattermost`. Use the gateway's Rust HTTP and WebSocket clients for REST v4 and `/api/v4/websocket`. The adapter owns wire normalization, authenticated channel and user evidence, Markdown and file rendering, and Mattermost effect classification. The profile owner supplies settings, leases, policy, durable intake, native session and command authority, attachment staging and the outbox. [Mercury adapter types](src/messaging/types.rs) · [Hermes Mattermost manifest](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/mattermost/plugin.yaml)

- **Setup and identity.** Configure an operator-selected HTTPS server base URL, including a deployment subpath when present, and a scoped bearer token ref. Prefer the server's dedicated bot account workflow. Support explicit personal access token setup for authorized user-account operation, with the authenticated sender identity shown privately to the owner. Verify `GET /api/v4/users/me` and bind its user ID to the verified deployment and profile. Require account and channel permissions through the ordinary Mattermost roles. Support an operator-configured private trust root for self-hosted deployments within the same TLS validation boundary. Keep request credentials scoped to the configured server, including WebSocket authentication. [Mattermost bot accounts](https://docs.mattermost.com/developers/integrate/reference/bot-accounts) · [Mattermost personal access tokens](https://docs.mattermost.com/developers/integrate/reference/personal-access-token)
- **Lifecycle.** Grant one active intake lease per verified deployment and user. Same-account rotation preserves logical routes and receipts. A changed server or actor requires a verified binding. Fence stale socket events, credential writes and delivery attempts when the owner reconnects, disables or replaces a connection. Authenticate with the supported bearer header at the WebSocket upgrade so the account is verified when requesting replay. Track REST authentication, stream readiness, verified continuity, and send status separately. Detect permanent authentication rejection and stop the reconnect loop when credentials need owner action. Redact credentials and message bodies from diagnostics. [Mattermost WebSocket authentication](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/introduction.yaml#L181) · [Hermes Mattermost socket lifecycle](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/mattermost/adapter.py#L469)

## Durable intake, reconnect and history

Parse bounded WebSocket events under the verified lease. Handle `hello`, the ordered server event sequence, and `seq_reply` responses according to the v4 protocol. Derive a logical input from the verified deployment, account and Mattermost post ID, with its original channel and root as immutable admission and delivery evidence. Treat duplicate `posted` frames and REST copies as the same logical input. A conflicting reuse is a typed conflict. Route membership, archive and permission changes to scoped binding updates. Treat edits, deletes and system events as typed state changes or refusals, with no new turn for the same post. Refuse specialized or expiring post types whose retention Mercury cannot honor. Update or retire authorized quote context when its source changes scope or is removed. [Mattermost WebSocket client](https://github.com/mattermost/mattermost/blob/v12.1.0/webapp/platform/client/src/websocket.ts#L350) · [Hermes Mattermost event normalization](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/mattermost/adapter.py#L584)

Record each input, disposition or recoverable preparation before advancing the safe prefix. Keep membership checks, attachment preparation and model work off the socket read loop. Commit the minimal evidence for any deferred work before advancing its cursor. Persist the authenticated server's `connection_id` and the next expected event sequence after the last committed disposition. On reconnect, use that pair for the `connection_id` and `sequence_number` query parameters. The `seq_reply` field tracks request responses independently of this cursor. Confirm continuity from the replay stream. A changed connection ID, sequence break or exhausted replay queue triggers repair or an explicit gap. Mattermost keeps bounded connection replay state. Server restart or failover can make it unavailable. The read position and an authenticated connection prove different things. [Mattermost server resume handling](https://github.com/mattermost/mattermost/blob/v12.1.0/server/channels/app/platform/web_conn.go#L162) · [Mattermost replay queue](https://github.com/mattermost/mattermost/blob/v12.1.0/server/channels/app/platform/web_conn.go#L516)

Recover a missed interval only in active, authorized channels and within configured age, page and event budgets. Persist the repair window and progress per affected channel. Use v4 channel post pagination to find known durable anchors and include thread replies. Stage live arrivals while repairing that channel, merge overlapping copies by original post ID, and release eligible inputs in established source order. Admit newly created eligible posts within the missed interval. An edited older post retains its prior input identity and creation boundary. Report gaps left by retention, revoked access or exhausted budgets. Unrelated routes continue. A first connection or newly authorized channel establishes a baseline, with old scrollback available only as bounded, authorized context. A restart reopens the existing baseline and pending work. [Mattermost channel post history](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/posts.yaml#L699) · [Gateway replay and intake](ADAPTER_CONTRACT.md#intake-ordering-and-execution-recovery)

## Authorization, sessions and controls

- **Rooms and mentions.** Resolve public and private channels, group messages and one-to-one DMs from verified channel metadata and current permission evidence. A one-to-one DM uses its DM grants and optional pairing. Other channels require the channel policy and current participant grant. Preserve team and channel scopes and handle DMs whose metadata has no team. Check the channel allowlist before mention rules, and use verified bot addressing with exact mention boundaries. Support explicitly enabled free-response rooms. A mention or membership change starts no work until the actor is authorized. Recheck restrictions at protected reads, native claim and dispatch. [Hermes Mattermost mention policy](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/mattermost.md#mention-behavior) · [Mattermost channel membership](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/channels.yaml#L1695)
- **Bots and loops.** Suppress the authenticated account's own posts as input, while preserving exact send evidence when available. Recognize peer bot accounts from server-verified provenance and explicit configured user IDs for peers using personal tokens. Treat bot handoff as a separate grant, with mention or free-response mode and the native loop guard. A display name or user-provided prop grants no bot authority. Keep status and progress quiet for bot-to-bot work. [Hermes peer bot handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/mattermost/adapter.py#L584) · [Mattermost post identity handling](https://github.com/mattermost/mattermost/blob/v12.1.0/server/public/model/post.go#L648)
- **Thread and session bindings.** Use `root_id` for an existing thread and verify the root belongs to the same authorized channel. In configured thread mode, an accepted top-level channel post is the reply root. Default unthreaded inputs to flat replies. An existing thread can use flat delivery only with an explicit route policy authorizing the parent audience. Keep participant-isolated or shared session bindings independent of the exact reply destination. Preserve root and channel on every progress post, chunk, control prompt, attachment and notification. Resolve linked or quoted post context only through authorized source reads. A moved, removed or unavailable root cannot silently reroute an existing intent. [Hermes Mattermost reply mode](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/mattermost.md#reply-mode) · [Mattermost create post and thread fields](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/posts.yaml#L1)
- **Native interactions.** Route supported slash-style commands, skills, session and model selection, queue, steering, stop, approvals, clarification and proactive target setup through the native authority. Document a normal addressed post such as a bot mention followed by the command when a Mattermost client reserves a leading slash for server commands. Match text approvals and clarification against the exact actor, prompt, route, expiry and execution generation. Load owner-configured channel prompts and other scope overrides at native claim. Keep channel prompt text transient and scoped to the turn, including when a session is shared. [Hermes Mattermost channel prompts](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/mattermost.md#per-channel-prompts) · [Shared command contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins)

## Delivery, presentation and media

**Posts and progress.** Render supported Markdown and split long content on Unicode-safe boundaries within the qualified server and adapter budget. Set the conservative Hermes chunk budget of 4,000 characters by default. Support typing and configured threaded tool progress and streaming previews. Create a progress post once under its authorized root and edit its confirmed post through `PUT /api/v4/posts/{post_id}/patch`. Finalize from the committed outcome. Suppress mentions in automatic output, including edits and captions. Use quiet progress publication on servers and credentials that support it, with typing or a committed final as the ordinary alternative when quiet rich progress is unavailable. A channel-wide or member mention needs explicit policy. [Hermes formatting and progress send paths](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/mattermost/adapter.py#L283) · [Mattermost post and patch API](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/posts.yaml)

**Files and voice.** Stage file IDs from the verified original post after account, channel, thread and actor policy permits the read. Fetch authorized bytes from the same Mattermost server under bounded streams and quota, validate media type and actual size, and support media-only posts. Use the profile's transcription and synthesis for voice workflows. Return images, documents, video and audio as native files. For upload, send bounded multipart requests to the authorized channel via `POST /api/v4/files`, commit the returned file IDs, then publish them in an ordered post to the intended channel and root. Split image and file batches at the provider's five-file per-post cap and preserve captions. Keep upload and publication separate so recovery reuses confirmed uploads and preserves the ordered receipt of each batch. Resolve authorized external image references through the host's scoped fetch, with a permitted link presentation if fetching is definitively unavailable before publication. [Mattermost v4 files API](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/files.yaml) · [Hermes Mattermost media batches](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/mattermost/adapter.py#L423)

**Delivery evidence and retry.** Record each ordered part and exact request, including a unique `pending_post_id` for create-post correlation, before dispatch. Record the accepted post ID from the REST result. An authenticated own-post observation can settle a lost response when it carries exact provider evidence linking the assigned key to the same author, channel, thread and prepared effect. Use notification acknowledgements for their documented notification purpose. Acceptance recovery requires a verified post identity and its exact effect association. Mattermost's current create-post cache uses a short expiry, 30 seconds in the reference source. Its expiry, possible eviction and continuity across restarts or nodes are distinct from Mercury's durable receipt. Default to holding ambiguous creates until exact evidence or owner resolution. Allow retransmission only where the deployment demonstrates the shared contract's stronger guarantee for that exact request. A provider in-progress or cache-related failure does not establish non-acceptance. [Mattermost create-post cache](https://github.com/mattermost/mattermost/blob/v12.1.0/server/channels/app/post.go#L125) · [Shared delivery and recovery](ADAPTER_CONTRACT.md#delivery-and-recovery)

Apply rate-limit deadlines to the affected verified server and account or narrower resource. Use bounded retries after definite non-acceptance. A lost file allocation, publication or edit response follows the same outbox uncertainty rules. A thread may become unavailable while work runs. Retain the original intent and provide an operator-visible blocked result. Only an explicitly authorized final notification can fall back to its parent channel after definite thread rejection, with authorization for that audience. Progress stays on its original thread. [Hermes thread failure behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/mattermost/adapter.py#L183) · [Mattermost API rate limits](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/introduction.yaml#L133)

**Proactive targets.** Use verified DM, channel or thread home targets for routines, signed webhook results, background runs and authorized manual sends. Accept a channel ID before its first native turn after verifying access and write permission. Resolve or provision a personal DM for an approved recipient through the supported channel API under the shared lease. Retain its verified pair and channel ID before publishing. A stored route or previous membership is insufficient following revocation. All sends use the owning gateway's receipts and outbox. [Hermes Mattermost home channel](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/mattermost.md#home-channel) · [Mattermost direct channel API](https://github.com/mattermost/mattermost/blob/v12.1.0/api/v4/source/channels.yaml#L136)

## Implementation and acceptance

| Work | Depends on | Ready when |
| --- | --- | --- |
| Connection and permissions | Shared stock-plugin gate and Microsoft Teams live acceptance | Profile setup verifies the server and account, the WebSocket authenticates and reports readiness, and the real owner fences revoked or stale generations. |
| Intake, repair and sessions | Verified connection and shared durable ingress | Exact duplicates, gaps and bounded overlap recovery pass with DMs, groups, channels, bot gating, per-channel prompts and thread routing. |
| Controls, files and outbox | Authorized routes and shared control and delivery contracts | Native commands and prompt responses, bounded media and voice, quiet progress, exact receipt recovery and producer delivery pass the transport suite. |
| Live acceptance | Completed Mattermost transport checks and shared conformance | A qualified Mattermost server and real clients prove authorized chat, thread, media and proactive workflows through reconnect and service restart. |

Drive scripted v4 REST and WebSocket endpoints through the production adapter, the real Mercury profile owner, disposable storage and a deterministic provider. Exercise the shared attachment and audio seams. Run the Mattermost transport suite, shared polling and push conformance, and `cargo test --locked --workspace`. [Mercury owner tests](tests/owner.rs) · [Hermes Mattermost fixtures](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/gateway/test_mattermost.py)

| Transport case | Evidence |
| --- | --- |
| Verified setup and replay | Reject a wrong server or account and stale lease. Recover a same-connection replay, then a fresh connection with only partial history. Restart after durable repair staging. Verify the overlap merges once, an edit does not become another turn, unavailable intervals are visible, and an unrelated channel proceeds. |
| Channel policy and interaction | Exercise DMs, group messages, a denied channel, an addressed and an opted-in channel, and a verified peer bot. Preserve original thread and participant scope. Change an owner channel prompt or revoke membership before claim. Verify a stale or foreign text approval cannot settle another request. |
| Media and status | Reject denied, oversize and foreign-channel media before use. Verify media-only turns, voice, batch upload receipts and exact thread publication across restart. Test edit and progress scopes, and ensure previews or copies of quoted text do not notify unrelated users. |
| Sends, roots and producers | Recover an exact send observation before or after HTTP completion. Hold a lost response with no exact evidence after deduplication expiry or server replacement. Exercise a definite rate limit, a deleted or moved thread root, and configured proactive delivery without duplicate posts. |

For live acceptance, use a current supported Mattermost server and controlled accounts with a real client. Verify private setup, an authorized DM and group message, a mention and a denied scope, a channel reply and an existing thread, text controls, an attachment and a voice round trip, a quiet progress edit, and a routine or background result at the verified home target. Disconnect and restart Mercury while the server remains active. Check replay or repair, that the native session remains bound and that a committed result reaches the original destination once. Record the server release, edition, qualified replay behavior, and enabled capabilities. ## Scope

Exclude legacy Hermes configuration compatibility, deprecated server endpoints, and publishing through a separate standalone sender. This spec covers the messaging adapter. Mattermost server administration, plugin hosting, Calls and Playbooks are separate features. Desktop UI remains deferred. [Backend parity scope](../../BACKEND_PARITY_PLAN.md#scope)
