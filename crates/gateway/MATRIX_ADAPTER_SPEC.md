# Matrix stock plugin implementation spec

Register Matrix as a bundled Rust adapter with platform key `matrix`. Start after Signal passes live acceptance and the expanded shared stock-plugin contract passes conformance. A headless Mercury profile can serve authorized Matrix DMs, rooms and threads on a supported homeserver, including encrypted conversations. The reference is the bundled Matrix platform in Hermes v0.23.4, with transport behavior based on the current Matrix Client-Server API. [Shared gateway contract](ADAPTER_CONTRACT.md#shared-requirements-for-stock-plugins) · [Signal spec](SIGNAL_ADAPTER_SPEC.md) · [Hermes Matrix guide](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md) · [Matrix Client-Server API v1.19](https://spec.matrix.org/v1.19/client-server-api/)

## Architecture and setup

Put the factory in `hermes-gateway::messaging::matrix`. Mercury owns policy, conversation bindings, intake, the execution queue and the outbox. The adapter owns validated Matrix Client-Server requests and room-event types, device setup, room state, and SDK-managed crypto. Use Matrix Rust SDK's published state, encryption and recovery components, including its vodozemac backend, with Ruma's typed Client-Server API. Drive sync through the adapter's bounded HTTP and durable handoff. Operate one SDK state and crypto store for each verified Matrix device in its private profile. Protect the SDK crypto store with a key held in profile secret storage. [Gateway adapter types](src/messaging/types.rs) · [Matrix Rust SDK](https://github.com/matrix-org/matrix-rust-sdk) · [Matrix SDK sync state machine](https://docs.rs/matrix-sdk-base/0.19.1/matrix_sdk_base/struct.BaseClient.html#method.receive_sync_response)

- **Verify a device session.** The private owner configures an HTTPS homeserver and bot account. Support attachment of an operator-provisioned device access session and owner-completed OAuth authorization on servers that advertise it. Use the SDK's browser authorization flow with discovery, registered redirect, state and PKCE. Both paths produce the same verified device binding. Validate the configured or discovered homeserver origin before sending credentials. Verify the full MXID and device ID with `whoami`. Negotiate server and room capabilities and report a typed refusal when a workflow requires an unavailable capability. Protect access and refresh tokens as session credentials, serialize refresh under the lease, and persist its replacement before resuming dispatch. Unusable credentials or an abandoned refresh require owner reauthorization. No password login path. [Hermes access-token setup](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md#step-2-get-an-access-token) · [Matrix client authentication](https://spec.matrix.org/v1.19/client-server-api/#client-authentication) · [Rust SDK OAuth](https://docs.rs/matrix-sdk/0.19.1/matrix_sdk/authentication/oauth/struct.OAuth.html)
- **Fence account and device state.** A verified Matrix account has one active Mercury intake lease. Scope the SDK store, sync tokens and pending protocol effects to the verified homeserver, MXID and device as applicable. Same-device token refresh preserves the device state. A new device can reopen the original account's room bindings after verification and current policy checks. It starts a new crypto and device replay scope, with earlier receipts preserved. Isolate stores and credential callbacks across profiles and reject stale generations. Status shows setup, sync continuity, encryption, verification and send readiness with credentials, recovery keys and private event content redacted. [Hermes Matrix device and store behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/matrix/adapter.py#L929) · [Matrix access tokens and devices](https://spec.matrix.org/v1.19/client-server-api/#relationship-between-access-tokens-and-devices)
- **Qualify the native build first.** Pin a maintained SDK release that builds and passes the crash-boundary fixtures below. Align the gateway and SDK onto one SQLite binding before integration. The reference SDK 0.19.1 SQLite store uses rusqlite 0.40.x and Mercury currently uses 0.43.x, which resolve to different native SQLite bindings. Verify the selected compatible dependency set with the existing profile storage tests and supported Windows, macOS and Linux builds. Use the same native adapter on those hosts. [Matrix SDK SQLite dependencies](https://github.com/matrix-org/matrix-rust-sdk/blob/matrix-sdk-0.19.1/crates/matrix-sdk-sqlite/Cargo.toml) · [Mercury gateway dependencies](Cargo.toml)

## Sync, durable intake and recovery

Use the stable `/_matrix/client/v3/sync` API. Send each request with the last Mercury-committed `since` token. Durably stage each bounded sync response under the current device lease before allowing SDK state or crypto processing to consume it. Record the incoming batch boundary, the next token, eligible room event identities and any limited timeline. Commit every relevant item's intake, refusal or recoverable preparation state before advancing to the next request. Apply SDK state and to-device work ahead of the dependent room events. Store raw ciphertext and safe references for pending events with unavailable keys. Never use the SDK's cached token or an empty duplicate callback as proof that a batch reached Mercury intake. [Matrix sync and gaps](https://spec.matrix.org/v1.19/client-server-api/#syncing) · [SDK sync token persistence](https://github.com/matrix-org/matrix-rust-sdk/blob/matrix-sdk-0.19.1/crates/matrix-sdk-base/src/client.rs#L626)

On restart, finish the journaled batch with the same verified SDK store before issuing a later sync. If the SDK already committed its state for that batch, use the staged event records and recovered room state and keys to finish outstanding Mercury dispositions. Retain the exact raw encrypted room event until it can be decrypted through the SDK or reaches a scoped terminal disposition. A replay, redelivery or late key must resolve to the original logical input. A batch can move the sync token beyond pending decryption once the work needed to retry each item is durable. Key arrival, corrupt ciphertext, unavailable trust, and deadline expiry have distinct dispositions. Retire temporary staged payloads once the durable intake and SDK state can support recovery. Preserve order in the affected route while pending input can be recovered. If the encrypted envelope leaves its thread scope unclear, hold that room's ordinary input until the scope or terminal disposition is known. Independent rooms can continue. [Matrix end-to-end encryption](https://spec.matrix.org/v1.19/client-server-api/#end-to-end-encryption) · [Gateway intake recovery](ADAPTER_CONTRACT.md#intake-ordering-and-execution-recovery)

Scope logical input by verified account, room ID and Matrix event ID. Process state, membership, device lists, invitations, and authorized reactions in their typed paths. Deduplicate the same event whether it appears in sync, authorized backfill, or retry after decryption. Redactions or replacements are changes to the existing event, never fresh commands or ordinary turns. A redaction can retire pending preparation or quote context under the shared data policy. A first sync or join establishes a room baseline. Process newly eligible events during setup once and keep old history contextual. For a limited timeline, persist its gap and `prev_batch`, then page bounded authorized history to a known durable boundary before admitting eligible missed events in that room. Stop on retention, access or budget limits and expose the remaining gap. Use the same admission identities for recovered and live messages. Context-only scrollback and first-sync history produce no agent work. [Matrix room history pagination](https://spec.matrix.org/v1.19/client-server-api/#get_matrixclientv3roomsroomidmessages) · [Hermes Matrix sync lifecycle](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/matrix/adapter.py#L1714)

## Room authority, sessions and threads

- **Rooms and invitations.** Honor explicit room and MXID rules, DM pairing, membership and power levels, and per-room operator and execution policy. An authorized invitation can queue a scoped join under the same verified room ID. Verify membership before routing work or publishing. Record direct-chat evidence from the accepted direct invitation, authenticated `m.direct` account data and eligible participant state, or an explicit owner binding. A two-person room can qualify for DM presentation, with authorization applied independently. A name, alias, membership count or invite hint alone supplies no permission to bypass a room restriction. Recheck membership and power at claim, protected reads and external effects. Room upgrades and alias changes require explicit rebinding of a different room ID. [Hermes room allowlists](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md#room-allowlist-allowed_rooms) · [Matrix direct messaging](https://spec.matrix.org/v1.19/client-server-api/#direct-messaging) · [Matrix invite authorization fixtures](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/tests/gateway/test_matrix_pending_invite_auth.py)
- **Triggers and scope.** Allow DMs without a mention under their grant. Use mention gating by default in multi-user rooms, with explicit free-response rooms, strict thread mention policy or authorized continuation in a thread where the bot has participated. Validate structured `m.mentions` and explicit Matrix IDs. Suppress self events, ignored bridge actors and protocol notices by default. An opt-in notice or known peer bot still uses the exact actor and room grants and the native loop guard. Bot notices cannot start DM pairing. Keep a distinct native binding for each DM, room or thread, and per participant in a shared room unless policy explicitly shares the session. Provide scoped room and project context in status and the model's attributed input. Require explicit source and destination authorization to resume a session in a different room. [Hermes Matrix behavior and project scope](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md#project-room-isolation)
- **Thread and quote routing.** Use the existing root event ID for `m.thread`. To auto-thread an unthreaded room input, use its event ID as the root of the reply path. Support an unthreaded room session and independent DM auto-thread and mention-triggered thread options. Preserve the root and reply anchor separately on each receipt, including chunks, attachments, interactive prompts and proactive results. Render the Matrix reply fallback without reintroducing quoted text as a new instruction. A reply or linked event is context only after verifying its room, visibility, and exact reference. An explicit native handoff may publish an authorized root event and bind the returned ID. [Matrix threads](https://spec.matrix.org/v1.19/client-server-api/#threading) · [Hermes thread and reply handling](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/matrix/adapter.py#L1922)

## Encryption and recovery

Support three setup modes. `off` is the default and serves authorized unencrypted rooms. `optional` can continue serving those rooms if crypto or device verification is unavailable and exposes the condition. `required` fails activation when crypto initialization or the device identity cannot be verified. Evaluate encrypted-room eligibility independently of connection mode. A known encrypted room or an explicit encryption requirement always needs verified crypto for protected content. Protect messages, captions, media bytes, previews and approval text under the authorized room's encryption. Matrix can expose protocol metadata such as reactions and read receipts. Verify sender and current device evidence through the SDK under the room's trust policy before admitting decrypted work. Permit this only through the route's configured capability and use encrypted text controls where reaction metadata is disallowed. [Hermes encryption modes](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md#enable-e2ee) · [Matrix SDK room-event encryption](https://github.com/matrix-org/matrix-rust-sdk/blob/matrix-sdk-0.19.1/crates/matrix-sdk/src/room/futures.rs#L204)

Use the SDK for device identity, one-time and fallback keys, room-key distribution, decryption, trust and cross-signing. Support owner-controlled verification, restoration from a supported recovery key and backup, and private enrollment of a fresh device when needed. Deliver a generated recovery secret only through the private owner setup flow. Persist protected crypto state across normal restarts. If stored device keys disagree with the verified server identity, stop using that device and surface the recovery state. A new device or trust refresh never silently changes the destination of a pending effect. Re-evaluate current room membership, visibility and recipient device eligibility before releasing a protected effect. Keep crypto keys and decrypted data confined to the scoped adapter, profile stores, and authorized native work. [Hermes Matrix cross-signing](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md#cross-signing-verification-recommended) · [Matrix SDK recovery](https://docs.rs/matrix-sdk/0.19.1/matrix_sdk/encryption/recovery/index.html)

## Controls, media and delivery

**Commands and presentation.** Route recognized `/command` and `!command` forms through the native catalog. Preserve unknown exclamations as text and keep stripped quote fallback separate from command input. Support session and model selection, text and reaction-backed approval and clarification choices, queue, stop and steering, skills and proactive target setup where authorized. Bind a reaction to the original prompt event, room and thread, intended actor or authorized role, action, expiry and request generation. Durably claim a decision once, refuse stale or foreign actions, and retire confirmed bot markers under the shared cleanup authority. Offer configured typing, scoped read receipts, processing reactions, and threaded editable progress or stream previews. Use `m.replace` on the confirmed bot event and the committed final result for finalization. Publish plain text and sanitized Matrix HTML, with bounded UTF-8 chunks and supported math markup. Use the Hermes-compatible 15,000-byte content budget with room for protocol and encryption overhead. Emit structured mentions under policy and require explicit permission for whole-room notifications. [Hermes Matrix controls](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md#matrix-tools-and-controls) · [Matrix event relationships](https://spec.matrix.org/v1.19/client-server-api/#forming-relationships-between-events)

**Media and voice.** Stage authorized images, documents, video and audio using the authenticated homeserver media API for `mxc://` content. Validate actual bytes and type. Bound uploads and downloads by the configured cap, 100 MiB by default, and the applicable homeserver and profile quotas. A Matrix event cannot direct the adapter to download an arbitrary URL. For encrypted attachments, validate the encrypted descriptor and integrity through the SDK and release only authorized decrypted bytes. Upload ciphertext and encrypted thumbnails for protected media. Persist separate preparation evidence for the returned content URI and the visible room event. Preserve captions, quotes and thread context across ordered image batches. Use profile transcription and synthesis and support native Matrix voice-message metadata for clients that render it. Keep ordinary audio files as audio attachments. In mention-gated rooms, a later bare mention from the same verified actor and exact room or thread can claim one preceding voice clip in a bounded queue. The default claim window is two minutes. Commit both identities and expiry before preparation. A denied or unclaimed clip stays unfetched and untranscribed. [Matrix authenticated media](https://matrix.org/docs/spec-guides/authed-media-servers/) · [Hermes attachment limits](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/website/docs/user-guide/messaging/matrix.md#media-limits) · [Hermes voice mention behavior](https://github.com/NousResearch/hermes-agent/blob/v0.23.4/plugins/platforms/matrix/voice_mention.py)

**Outbox and exact retry.** Use a stable transaction ID for room event sends where the server supports Matrix device-scoped deduplication. Record the exact homeserver, device, endpoint, room and event type, transaction ID, and immutable prepared request before dispatch. For encrypted events persist the sealed ciphertext, with key-sharing and eligibility established for that attempt. On loss of the response, consult exact sync echo evidence such as the matching `unsigned.transaction_id` when supplied for the sending device. The original room event ID is acceptance evidence. Replay the identical request only while the qualified server's deduplication horizon and the original device, destination, audience protection and current policy remain valid. A new device or changed endpoint cannot carry over this guarantee. Outside verified replay conditions, keep the attempt uncertain pending exact evidence or owner resolution. A media allocation, upload, or other operation without the same guarantee uses its own classification. Respect `Retry-After` and retain cooldown scope. Route scheduled, webhook, background and authorized manual results through the same outbox to verified rooms or threads. [Matrix transaction identifiers](https://spec.matrix.org/v1.19/client-server-api/#transaction-identifiers) · [Matrix send events](https://spec.matrix.org/v1.19/client-server-api/#put_matrixclientv3roomsroomidsendeventtypetxnid) · [Synapse transaction retention](https://github.com/element-hq/synapse/blob/develop/synapse/storage/databases/main/events_worker.py#L2407)

## Scope

Exclude Hermes environment and crypto-store migrations, legacy password login, deprecated unauthenticated media download, libolm, the old Sliding Sync proxy, and Hermes's Linux container and agent forwarding workaround for native encryption. Application services, account administration, federation hosting, arbitrary model-driven room administration, and Matrix calls are outside this stock messaging spec. Desktop UI remains deferred.
